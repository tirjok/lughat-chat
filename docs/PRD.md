# PRD: Lughat Chat — Arabic Text-to-Speech Web Application

## Problem Statement

Users need a local, free, offline-capable web application that converts Arabic text into natural-sounding speech. Existing solutions require cloud APIs (cost per character), lack quality Arabic support, or require complex setup. Users want a single command to run everything locally with no external dependencies after initial startup.

## Solution

A Dockerized web application consisting of:
- **Backend**: Python FastAPI with XTTS-v2 neural TTS model running locally on CPU
- **Frontend**: Nuxt.js SPA with RTL Arabic UI, served via Nginx
- **Deployment**: Single `docker compose up` command starts both services, with Nginx reverse proxy routing all traffic through port 80

The model downloads once (~2GB) on first start, then persists in a Docker volume for instant subsequent startups.

## User Stories

1. As a user, I want to type Arabic text into a textarea so that the app can convert it to speech
2. As a user, I want the UI to be fully RTL (right-to-left) so that Arabic text feels natural
3. As a user, I want to hear the generated audio immediately after clicking "Generate" so that I can verify quality
4. As a user, I want to download the generated audio as an MP3 file so that I can use it offline
5. As a user, I want to adjust speech speed (0.5x–2.0x) so that the output matches my preferred pace
6. As a user, I want to select between male and female voice presets so that the output matches my preference
7. As a user, I want to see a loading indicator while the TTS model is being generated so that I know progress
8. As a user, I want the first startup to download and cache the TTS model automatically so that subsequent startups are instant
9. As a user, I want to run the entire application with a single command (`docker compose up`) so that setup is trivial
10. As a user, I want the application to work completely offline after initial startup so that no internet is required
11. As a user, I want the model to persist across container restarts so that I don't re-download it every time
12. As a user, I want to see error messages in Arabic so that I understand what went wrong
13. As a user, I want keyboard shortcut (Ctrl+Enter) to generate speech so that I can work quickly
14. As a user, I want the audio player to show progress bar and play/pause controls so that I can control playback
15. As a user, I want the application to run on my Mac M1 without requiring GPU so that it works on any machine
16. As a user, I want the generated audio to be high quality (neural TTS) so that it sounds natural
17. As a user, I want the application to handle Arabic text with proper diacritics and punctuation so that pronunciation is correct
18. As a user, I want to access the application at http://localhost so that no special configuration is needed

## Implementation Decisions

### Architecture
- **Two containers** orchestrated by Docker Compose: backend (FastAPI + TTS) and frontend (Nuxt.js → Nginx)
- **Single port (80)** — Nginx reverse proxy routes `/api/*` and `/downloads/*` to backend, serves SPA for everything else
- **No CORS needed** — all traffic goes through Nginx, eliminating cross-origin issues

### TTS Engine
- **Model**: XTTS-v2 (Coqui TTS) — multilingual neural TTS with Arabic support
- **Runtime**: CPU-only PyTorch (no GPU required, runs on Apple Silicon via Docker Linux emulation)
- **Model delivery**: Downloaded at container startup, cached in named Docker volume (`tts-model-cache`)
- **Audio format**: WAV generated by XTTS → converted to MP3 via ffmpeg (192kbps)

### Backend API
- **Framework**: FastAPI with async endpoints
- **Endpoints**:
  - `POST /api/generate` — Synthesize text to speech (returns MP3 blob)
  - `GET /api/voices` — List available voice presets
  - `GET /health` — Health check returning model load status (`loading` | `ready` | `error`)
  - `GET /api/history` — List previously generated audio files
- **Model loading**: Loads on startup, status tracked via health endpoint
- **Audio storage**: Named volume (`tts-audio-cache`) persists generated files across restarts

### Frontend
- **Framework**: Nuxt.js 3 with TypeScript
- **Styling**: UnoCSS (utility-first CSS framework)
- **UI Features**: RTL layout, Arabic text input with character counter, speed slider, speaker selector
- **Audio Player**: Custom controls (play/pause, progress bar, seek, download) using Blob API
- **Model Loading**: Polls `/health` endpoint every 2 seconds, shows loading indicator until model is ready
- **Error Handling**: Arabic error messages displayed in toast notifications

### Deployment
- **Docker Compose**: Two services (`backend`, `frontend`) with named volumes for model and audio persistence
- **Health checks**: Backend health check retries 20 times with 60s start period (accommodates model download)
- **Frontend dependency**: Waits for backend to be healthy before starting
- **Image sizes**: Backend ~500MB (CPU-only PyTorch), Frontend ~20MB (Nginx Alpine)

### API Contract
```typescript
// Request
interface SynthesisRequest {
  text: string          // Arabic text, 1-3000 characters
  language: 'ar' | 'en' // Default: 'ar'
  voice: 'female' | 'male' // Default: 'female'
  speed: number         // 0.5 - 2.0, default: 1.0
}

// Response (MP3 blob)
interface SynthesisResponse {
  audio_url: string     // /downloads/{filename}
  filename: string      // {lang}_{voice}_{timestamp}.mp3
  duration_seconds: number
}

// Health check
interface HealthResponse {
  status: 'loading' | 'ready' | 'error'
  model_loaded: boolean
}
```

## Testing Decisions

### What makes a good test
- Test external behavior only (inputs → outputs), not implementation details
- Backend: Test API endpoints with mocked TTS model, verify request/response schemas
- Frontend: Test composable logic (audio player state management) in isolation
- Integration: Verify Docker Compose stack starts and services communicate

### Modules to test
1. **TTS Engine Module** — Unit tests for audio conversion (WAV → MP3), error handling
2. **API Gateway Module** — Integration tests for all endpoints (generate, health, voices)
3. **Audio Player Module** — Unit tests for playback state transitions (play → pause → end)
4. **UI Module** — Component tests for RTL input validation, loading states

### Prior art
- Existing `app.py` has FastAPI structure with Pydantic models — easy to add pytest fixtures
- Existing composables (`useAudioPlayer.ts`, `useTtsApi.ts`) are pure functions — easy to unit test
- No existing test infrastructure in the codebase

## Out of Scope

- Voice cloning / speaker embedding (XTTS-v2 supports it but not implemented)
- Real-time streaming audio (generates full file, then returns)
- Multi-user support / authentication
- Cloud deployment (designed for local Docker Compose only)
- GPU acceleration (CPU-only, works on any machine including M1 Macs)
- Batch processing / queue system (single request at a time)
- Text-to-phoneme preprocessing or Arabic normalization beyond what XTTS-v2 handles natively

## Further Notes

### Divergence from Original PRD
The original planning document (docs/PRD.md) assumed:
- Model baked into Docker image → **Changed**: Downloaded at runtime, cached in volume (smaller images)
- GPU support assumed → **Changed**: CPU-only (no CUDA on Mac, Docker Linux emulation)
- Separate ports for frontend/backend → **Changed**: Single port via Nginx reverse proxy (no CORS)
- SSR frontend → **Changed**: Static build + Nginx serving

### First Startup Experience
1. User runs `docker compose up --build`
2. Backend container starts, downloads ~2GB XTTS-v2 model to volume (5-10 minutes)
3. Frontend shows "جاري تحميل النموذج..." with spinning loader
4. Once model loads, indicator changes to checkmark "النموذج جاهز"
5. User can immediately start generating speech

### Subsequent Startups
1. `docker compose up` (no --build needed)
2. Model loads from volume in seconds
3. Application ready immediately
