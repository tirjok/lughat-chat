# ADR-014: Backend Modular Monolith — Deep Domain Modules

**Status:** Accepted
**Date:** 2026-07-18
**Decision:** Restructure the monolithic `app.py` (1110 lines) into a thin controller with four deep domain modules.

## Context

ADR-001 mandated a Modular Monolith architecture with four modules (Content, Progress, TTS, API) but the implementation remained a single 1110-line `app.py` file. This file mixed:

1. **TTS synthesis** (model loading, speech generation, FFmpeg conversion)
2. **Content management** (lesson JSON scanning, SQLite initialization)
3. **Learning management** (progress tracking, activity submission, sequential unlocking)
4. **Infrastructure** (torch patching, sidecar I/O, cleanup, voice resolution)

This violated ADR-001's explicit module boundaries and made the codebase:
- Untestable without FastAPI/HTTP (no module-level testability)
- Hard to maintain (business logic duplicated across 3 endpoints)
- High cognitive load (4 domains in one file)

## Decision

Restructure the backend into these modules:

```
backend/
├── app.py              (~130 lines) thin FastAPI controller
├── config.py           (~40 lines)  path constants
├── lifespan.py         (~60 lines)  model loading + DB init
├── schemas.py          (~150 lines) request/response models
├── db/                 (data access layer)
│   ├── __init__.py     get_db_connection()
│   ├── safety.py       apply_safety_pragmas()
│   ├── lessons_db.py   init_lessons_db()
│   └── progress_db.py  init_user_progress_db()
├── content/            (existing — unchanged)
│   ├── __init__.py
│   └── scoring.py      5 scoring algorithms
├── tts/                (NEW — TTS domain)
│   ├── __init__.py     exports TtsEngine
│   ├── engine.py       TtsEngine class (~370 lines)
│   ├── audio_pipeline.py  _discover_voices, _cleanup_audio_dir
│   └── voice_resolver.py  resolve_voice()
├── learning/           (NEW — Learning domain)
│   ├── __init__.py     exports LessonService
│   └── service.py      LessonService class (~550 lines)
├── storage/            (NEW — Storage domain)
│   ├── __init__.py     exports StorageService
│   ├── service.py      StorageService class (~180 lines)
│   └── helpers.py      write_sidecar, read_sidecar, cleanup
```

### Module responsibilities

| Module | Exports | Depends on |
|--------|---------|-------------|
| `tts.TtsEngine` | `load_model()`, `synthesize()`, `health()`, `discover_voices()` | `tts.audio_pipeline`, `tts.voice_resolver` |
| `learning.LessonService` | `list_lessons()`, `get_lesson()`, `submit_activity()` | `content.scoring`, `db` |
| `storage.StorageService` | `get_history()`, `cleanup()`, `discover_voices()` | `storage.helpers` |
| `app` | 8 route handlers (~10 lines each) | All domain modules |

### Backward compatibility

Existing tests reference `app.tts_model`, `app.model_load_status`, `app.AUDIO_DIR`, `app._get_db_connection()`, `app.discover_voices()`, etc. The new `app.py` re-exports these as module-level attributes so existing test code continues to work without modification.

## Consequences

1. **app.py shrinks from 1110 → ~130 lines** — 8 route handlers, each ~10 lines.
2. **Three duplicated status resolution algorithms** (in `list_lessons`, `get_lesson`, `submit_activity`) consolidated into `LessonService._resolve_lesson_status()`.
3. **Business logic concentrated in deep modules** — `TtsEngine`, `LessonService`, and `StorageService` are testable without FastAPI/HTTP.
4. **Module-level testability** — each domain module can be unit-tested independently.
5. **Migration is non-breaking** — all 22 existing test files work without modification.

## Migration steps (4 phases)

1. **Extract schemas** — move Pydantic models to `schemas.py` (done).
2. **Extract TTS module** — move model loading, synthesis, voice resolution to `tts/` (done).
3. **Extract learning module** — move lesson/progress/submit logic to `learning/` (done).
4. **Extract storage module** — move audio history/cleanup/voice discovery to `storage/` (done).

Each phase produces independently testable code.
